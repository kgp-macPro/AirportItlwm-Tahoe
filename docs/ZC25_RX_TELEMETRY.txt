ZC25 RX forced/periodic saved-plist decoder
=========================================

This is an offline decoder. It never invokes ioreg, reads live hardware, changes
settings or generates traffic. Python3 standard library only. Usage:

python3 tools/decode_zc25_rx.py /path/to/saved.plist > /path/to/decoded.json

It accepts saved XML or binary plists. Recursively searches dictionary/list
providers, requires exactly one health/experiment provider, exact marker
AirportItlwm-Tahoe-B1-ZC25-PERF, and exact KGP_ZC19 schema19/1 256 bytes.
Mode must be1(conventional) or2(mapped); mode0(unqualified) is rejected. Present
malformed main/pressure OSData is rejected even in conventional mode. Ambiguous
providers are not silently filtered/selected. Decoder errors return2 with no
partial JSON on stdout. Fault states remain in forensic output; this decoder is
not a benchmark health PASS gate.

Original properties remain losslessly represented as raw_hex and raw_qwords;
there is no replacement/merging of forced and periodic originals. All pressure
records are independently preserved. The decoder does not modify source plists.

Source grounding: exact active ZC25 ItlIwx.cpp inspected read-only in
/Users/kgp/Developer/OpenIntelWireless/AirportItlwm-Tahoe-1.0.0-Experiments/TRACK-B1-ZC25-PERF
at rxZcReport, rxZcCapturePeriodic, rxZcPublishPeriodic, rxZcPressureRecord,
KgpRxZcPool::snapshot, KgpRxZcLife/KgpRxZcStorage, and zc19Snapshot.

Selection and lifetime limitations
---------------------------------
Forced key: KGP_RX_ZC4. Periodic key: KGP_RX_ZC4_PERIODIC.
Both use original schema4, 64 little-endian64-bit words (512bytes), no revision
word. The reason distinguishes forced lifecycle capture from watchdog capture:
0 watchdog periodic;1 RXarm;3 terminal close;4 unproven-terminal close;
5 deferred-cleanup handoff. KGP_RX_ZC4 rejects reason0 and the periodic key
rejects any nonzero reason, matching this candidate's actual writers.

Health KGP_ZC19 is schema19/revision1/bytes256, 32little-endian64-bit words.
Current RX record must satisfy ALL:
  RX word11(rx generation) == health word6(driver generation)
  RX word12(posted RX reset epoch) == health word11(reset epoch)
  RX word13(recorded reset epoch) == health word11(reset epoch)
Only after this match are snapshot serials compared. No global highest serial
selection exists: RX setup resets serial, so an older lifetime can have a much
higher number. Forced reasons3/4/5 from other lifetimes are explicitly listed as
retained_other_lifetime_forced_keys and fully decoded rather than discarded.

A newer forced record wins over an older captured periodic record from the same
matching lifetime, even if that old periodic property was published later. If
no tuple matches, current_rx stays null with a warning; no fallback to old pool
state occurs. In conventional mode current_rx is always null because it has no
active mapped prepared pool; existing pool properties are historical evidence.

The generation/reset tuple is not a separate unique pool allocation ID. If a
tuple is reused and serial order contradicts local capture-time order, decoder
rejects ambiguity instead of allowing an old high serial to win. Equal serials
with conflicting records are also rejected. This does not prove every possible
tuple reuse is detectable; a future unique pool ID would be required for that.

IORegistry properties are NOT globally atomic, nor are pool fields sampled at
one hardware instant. The main gate capture, pool-lock gauges and independent
relaxed atomics are distinct observation boundaries. Pressure records contain
no generation/reset tuple and cannot be safely attributed to a pool lifetime by
their key alone. Epoch mismatches may indicate capture/publication timing; they
are not silently interpreted as DMA faults.

time2GNow uses clock_get_uptime plus absolutetime_to_nanoseconds: word17 and
pressure word2 are local monotonic boot uptime in nanoseconds, not UTC and not
the peer's clock. No one-way latency or peer delivery is derived.

counter is reinterpreted as packet loss, actual firmware delivery, TCP acceptance,
pool exhaustion or permanent mapping leak.

Pressure24-word schema, exact mapping
------------------------------------
Keys:
KGP_RX_ZC4_FIRST_PRESSURE, KGP_RX_ZC4_LAST_RECOVERY,
KGP_RX_ZC4_PERIODIC_FIRST_PRESSURE, KGP_RX_ZC4_PERIODIC_LAST_RECOVERY.
00 schema4;01 event1(firstpressure) or2(lastrecovery);02local uptime ns.
03..18 the same16 pool snapshot fields as main24..39 in the same order.
19 replaced;20 starved;21 PC1fault;22 RXfault;23life.detached.
There is no pressure serial, generation, reset epoch or unique pool ID.
Even though all current fields have source names, raw originals are retained;
their scope/timing limitations must not be hidden by decoded labels.
