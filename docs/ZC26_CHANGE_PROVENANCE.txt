SUPERSEDES the earlier optional SFENCE selection documented below. Before any
ZC26 Kext build, the packet helper was returned to full SEQ_CST, exactly the
ZC22 strength; both cold queue helpers also remain full SEQ_CST. Four actual
sites, all full. The per-site roles/read/write/lifetime review below remains
useful, but SFENCE is NOT in the delivered candidate. Architectural sufficiency
alone did not establish a stability benefit; the final user priority is a
reliable ZC22-class550/520RX and480TX, not tonight's580/580 prerequisite.
The source tests and final binary gate require the full barriers at all sites.
No optional throughput optimization is required to complete stability work.

FINAL candidate reconciles ZC22 control publication with ZC25 reporting outside
the RX gate, preserving all safety, plus independent command-error corrections.
Reporting relocation removes a SOURCE-PROVEN allocation/IORegistry publication
inside the traffic gate; it cannot by itself prove the old intermittent stalls'
cause. ZC25 retained good WAN but its jointly changed control layout had weaker
RX, so the chosen combination is a testable reconciliation, not established
physical stability. Do not claim collapses fixed until KGP evaluates it.

STORE-PUBLICATION CONTRACT (independent of cache policy)
There are TWO alternative packet publication sites and TWO cold queue setup
sites. Packet stores precede SFENCE and the actual MMIO WRPTR publication; queue
configuration retains its original full SEQ_CST before firmware command handoff.
The inline asm compiler memory clobber forbids compiler memory motion. x86
ordinary WB/UC LoadStore ordering and existing gate/acquire contracts retain
prior ownership reads; SFENCE provides only StoreStore ordering. Completion,
command, reset and stop atomics keep all original memory orders. Neither helper
is an RX DMA read invalidation or positive completion proof. Non-x86 packet
fallback stays full SEQ_CST. Final Release disassembly is a separate gate.

Primary reference: Intel SDM Vol2B SFENCE, document325383, page4-616:
https://cdrdv2-public.intel.com/782156/325383-sdm-vol-2abcd.pdf
Linux DMA memory-ordering contract reference (not code imported):
https://kernel.org/doc/html/latest/core-api/wrappers/memory-barriers.html
https://cdn.kernel.org/doc/html/latest/driver-api/io_ordering.html
Existing lock-prefixed ownership/counter operations may dominate cost. No actual
RX bottleneck, PAT/cache state or numerical speedup follows from instruction
counts. Negative ZC23/24/25 physical results remain constraints. No external
implementation code was copied; only ISA/documentation contracts were consulted.

INDEPENDENT COMMAND-STATUS CORRECTNESS REPAIR
A status helper receiving a nonnullfailed CPU response returnedEIO before freeing
its caller-owned response, unlike the bad-length branch. Free it on the same
failure branch, nullable/idempotent API as before. Current ordinary RX handlers
already filter CMD_FAILED responses before caller transfer, so this branch's
production reachability is NOT established. Do not call it an observed leak.
Transport-error ownership is unchanged: iwx_send_cmd transfers resp_pkt only on
successful wait, otherwise retains/frees its own response; command DMA ownership
and positive completion/quarantine never depend on this CPU response free.

Two SOURCE-PROVEN caller failures are fixed: iwx_add_sta_cmd set STA_ACTIVE when
transport err!=0 due to its compound if/else; it now returns the transport error
without asserting activation. iwx_add_aux_sta enabled an auxiliary queue after
transport error and replaced it with the queue-enable result; now returns error
before enabling. FirmwareADD_STA status failure remainsEIO; versions>=12 still
skip the legacy auxiliary path. Existing active bit is preserved on failedupdate,
not blindly cleared. All failures flow to existing initialization/recovery code.
These branches exist directly in frozenZC8 too. They are independent correctness
repairs, not an explanation of the ZC13chronology or a provenRX/firststatefix.
Actualhelper/PDU/free/fullaux/criticalstationtail tests inject both errno signs,
failed/short/missing/validresponse, FWstatuses and versions. No rate, queue-growth,
firmware binary, power policy or DMA-lifetime change.

FOCUSED FOUR-SITE REVIEW / CONSERVATIVE FINAL STRENGTH
Supersedes the earlier all-four-SFENCE proposal above before any Release build.
Only the two ALTERNATIVE packet TX paths useSFENCE. The default and dynamicTVQM
queue setup sites now call a separate fullSEQ_CST queue-publication helper;
their established initialization/command boundary strength is unchanged. These
rare setup operations are not a per-ACK cost, so weakening them has no supported
hot-path benefit. Their complete firmware-command/CPUhandoff lifecycle is kept
conservatively stronger even though the immediate data role is writepublication.

For TCP reception a driver-transmitted ACK executes ONE packet site, mapped OR
conventional. A completion does not automatically execute a fence: it must
actually cause a subsequent successful packet submission. Queueconfiguration
runs during setup/reconfiguration, not fourtimesperACK. Firmwarecommandqueue0
retains its own existing policy and command ownership; no frame-rate inferred.
Each packet's CPU ownership/acquire checks precede privateconstruction/payload
copy, publication stores and barrier. Existing x86LoadStore ordering plus compiler
memoryclobber prevents those reads crossing the hardwareownership submission;
SFENCE orders the CPUstores before the subsequent MMIOstore. Completion/token/
reset handshakes retain their existing atomicorders. SFENCE is not a CPU
StoreLoadhandshake, does not order RXloads, and does not imply devicecompletion.
Finalbinary must showtwoSFENCE packet sites andtwooriginalfullqueuebarriers.
No significance of the fullpacketbarrier as an actual RXbottleneck is claimed.
